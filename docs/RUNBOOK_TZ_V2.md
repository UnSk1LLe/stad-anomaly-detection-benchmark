## 1. Локально: закрыть этап 1

Команды однострочные — работают и в PowerShell, и в bash. `make` на машине нет,
поэтому везде `python ...`.

### 1.1 Синхронизация

```bash
git fetch origin
git checkout claude/bold-dijkstra-5zupbh
git pull
pip install -r requirements.txt
```

Проверить, что на месте данные и score обоих пилотов (240 клеток × 2 файла):

```bash
python -c "import glob; [print(d, len(glob.glob(f'reports/{d}/scores/*.npy'))) for d in ('ft_aed_cv', 'ft_aed_cv_both')]"
python -c "import os; print(os.path.getsize('data/ft-aed/nashville_freeway_anomaly.csv'))"
```

Ожидается 480 и 480 файлов и 123234268 байт. Меньше файлов — диагностика
отработает, но недостающие клетки попадут в раздел «Чего не хватает»; тогда
добавь к командам ниже `--recompute-nontrainable` (дособерёт небучаемые).

### 1.2 Тесты

```bash
python -m pytest tests -q
```

**Успех:** 158 passed. **Неудача:** дальше не идти; прислать вывод
`python -m pytest tests -x -q` целиком (с traceback). Тесты считают на CPU и не
зависят от `scores/` и `data/`, так что падение — расхождение окружения
(версии torch/pandas) или ошибка кода, а не данных.

Если скрипт падает с «датасеты конфига не совпадают с датасетами прогона

пилота (`git diff 7ca4d85 -- src/stad/data configs/data`). Не обходить: выяснить,
что изменилось, и сообщить.

## 2. Решение по разделу 9 — до любого пересчёта

Этап 2 целиком класса B. По ТЗ §0 агент не начинает его без отметок `[x]` в
разделе 9 `docs/TZ_PROTOCOL_V2.md`.

**Почему решать сейчас и пакетом.** Запрет на подгонку: вариант метрики нельзя
выбирать после того, как увидел, как он двигает таблицу. Если утверждать 2.1,
посмотреть пересчёт, а потом решать про 2.3 — это уже выбор по числам.
Утверди блок этапа 2 целиком (2.1–2.6 и δ для 2.4) одним коммитом до пересчёта.
Этапы 3–5 можно утвердить позже: их критерии зафиксированы в ТЗ заранее.

Как: поставить `[x]` в §9, вписать δ (предложение ТЗ — 0.05 по `padf_skill`) и
закоммитить отдельно:

```bash
git commit -am "ТЗ v2 §9: утверждены 2.1–2.6, δ = 0.05" -m "Решение принято до пересчёта по сохранённым score."
```

## 3. Дальнейшие этапы: где делать, критерий, развилка

`score` и чекпойнты есть только локально, поэтому всё, что их читает или обучает
модели, делается у тебя. Код и тесты на синтетике можно делать в облаке или
локальным Claude Code — тем же пайплайном (раздел 4).

| Задача | Где | Выход | Успех → | Неудача → |

## 4. Агентный пайплайн этапа 1

### 4.1 Схема

```
оркестратор (основная сессия)
  ├─ разведка: ТЗ, CLAUDE.md, PROTOCOL, DECISION_RULES, код; классы A/B; §9;
  │   есть ли данные и score; базовый прогон тестов; быстрая проба чисел
  ├─ общий контракт первым коммитом (stad.eventlog) — от него ветвятся все задачи
  │
  ├─ workflow implement-review-fix (docs/workflows/implement_review_fix.js)
  │    для каждой задачи независимо (pipeline, без барьера между задачами):
  │    Implement ── свой git worktree, ветка wf/<задача> от base,
  │    │            спецификация + жёсткие ограничения, полный набор тестов, коммит
  │    Review ───── два независимых ревьюера параллельно, read-only:
  │    │            «спецификация и протокол»  /  «баги и адекватность тестов»
  │    │            (мутационная проверка: сломать строку — тест должен упасть)
  │    Fix ──────── новая ветка wf/<задача>-final: проверить КАЖДУЮ находку,
  │                 реальные исправить, ложные отклонить с причиной, тесты, коммит
  │
  ├─ интеграция: squash-merge каждой -final ветки = один коммит на задачу ТЗ;
  │   полный набор тестов перед каждым коммитом; чтение диффов глазами
  ├─ находки по пути (класс A) — отдельным коммитом с тестом, который падает без правки
  └─ выход этапа: инструменты на реальных данных (сначала один фолд), механическая
      проверка критерия выхода (grep действий в разделе 5 RESULTS.md)
```

### 4.2 Что получает каждый агент

| Роль | Вход | Права | Выход (схема) |
|---|---|---|---|
| Implementer | общий преамбул (ограничения CLAUDE.md, запрет гейтовых путей, тесты, git) + спецификация задачи | правка кода в своём worktree | ветка, коммит, изменённые файлы, тесты, отклонения от спецификации, `blocked` |
| Reviewer «spec» | дифф ветки против base + та же спецификация | только чтение | находки: severity, файл, строка, доказательство, предложение |
| Reviewer «bugs» | то же | чтение + отдельный detached worktree для запуска тестов | то же |
| Fixer | ветка implementer'а + все находки + спецификация | правка в своём worktree | применённые / отклонённые с причиной, тесты, коммит |

Спецификация задачи — главное. Хорошая спецификация (пример — 
`docs/workflows/tz_v2_stage1.args.json`) содержит: точные файлы и сигнатуры;
что нельзя менять (чтобы параллельные задачи не конфликтовали); готовые
определения величин; **тест приёмки из ТЗ дословно**; известные числа для
сверки; что делать, если данных нет.

### 4.3 Почему так

- **Ревью отделено от реализации.** Автор не видит своих слепых пятен; две
  разные «линзы» ловят разные классы ошибок (на этапе 1 — 40 находок, из них
  реальные: неполнота по кредитам событий, ORACLE-таблица, отсортированная как
  лидерборд, вердикты в диагностическом CSV, вырожденный сквозной тест с одним
  событием).
- **Fixer проверяет находки, а не принимает их.** Ревьюеры тоже ошибаются;
  отклонение с причиной видно в отчёте.
- **Worktree на задачу.** Параллельные агенты не ломают друг другу рабочее
  дерево и тесты; интеграция — обычным merge.
- **Общий контракт до распараллеливания.** Иначе два агента пишут два разных
  `event_table`.
- **Один коммит на задачу ТЗ** (squash) — история читается по ТЗ, а не по
  итерациям агентов.

### 4.4 Грабли, на которые наступили

- **Worktree может создаться не от текущей ветки** (у двух агентов база была
  `master`). Поэтому в сценарии первая команда — `git checkout -b <ветка> <base>`
  и проверка `git log -1`.
- **Гейт `ask` в работе без присмотра = отказ.** Агент попытался `git reset` —
  hook отдал `ask`, в фоновом агенте это блокировка. В преамбуле прямо
  запрещены `git reset`, `git checkout --`, `rm -rf` и гейтовые пути.
- **Перезапуск машины теряет фоновые прогоны.** Fixer диагностики не успел
  закоммитить правки. Отсюда в сценарии: «commit early (WIP-коммит допустим)».
- **CPU.** Одновременно работают не больше `CPU − 2` агентов; каждый гоняет
  полный набор тестов. Тяжёлую проверку на реальных данных делать на одном
  фолде, полную — один раз после интеграции.
- **Не заходить оркестратором в worktree агента** (`cd`): рабочий каталог сессии
  переключается на него.

### 4.5 Как повторить у себя

**Вариант A — Workflow в Claude Code** (если инструмент доступен в твоей версии;
запускается только по явной просьбе):

1. Подготовить `args`: скопировать `docs/workflows/tz_v2_stage1.args.json`,
   заменить `repo` (абсолютный путь к репозиторию), `scratch` (каталог для
   временных файлов вне репозитория), `base` (коммит, от которого ветвиться) и
   `tasks` (ключ, ветка, спецификация каждой задачи).
2. Попросить Claude Code: «запусти workflow из файла
   `docs/workflows/implement_review_fix.js` с args из `<файл>.json`». Чтобы он
   стал именованным, скопировать скрипт в `.claude/workflows/` (это изменение
   пайплайна — гейт спросит подтверждение).
3. После завершения — интеграция вручную или попросить оркестратора:

```bash
git merge --squash wf/<задача>-final
python -m pytest tests -q
git commit
```

   повторить для каждой задачи; затем удалить отработанные worktree:
   `git worktree list`, `git worktree remove --force <путь>`.

**Вариант B — существующие агенты `.claude/agents`** (без Workflow):

| Роль сценария | Агент |
|---|---|
| оркестратор | `experiment-orchestrator` (или основная сессия) |
| implementer, fixer | `code-surgeon` — с выданным разрешением на класс B, если задача из §9 |
| reviewer ×2 | нужен read-only агент `code-reviewer` (ниже); `results-analyst` смотрит на числа прогона, а не на код |

Определение ревьюера — положить в `.claude/agents/code-reviewer.md` (изменение
пайплайна, гейт спросит подтверждение):

```markdown
---
name: code-reviewer
description: Read-only адверсариальное ревью ветки против базового коммита по заданной линзе (spec — соответствие ТЗ и CLAUDE.md; bugs — ошибки и адекватность тестов). Возвращает находки с доказательствами; ничего не правит.
tools: Read, Grep, Glob, Bash(git diff:*), Bash(git log:*), Bash(git show:*), Bash(git worktree:*), Bash(python -m pytest*)
```
